# data-analysis-task

> 关灯科技 · 实战任务。只使用任务页发放的 `data/audit_logs.csv`（1318 行）。
> 本文引用的每一个数字都来自 `uv run analyze.py` 的输出（`output/analysis.txt`），可逐条复算。

## 一句话结论

**根问题：初审时规则库「半旧」（距最近一次同步超过约 10 分钟）的案件退单率 42.9%，是规则新鲜组（2.5%）的 17 倍**——23% 的初审量贡献了 84% 的退单。对这组案件提前转人工初审，按题给成本口径净省 **6600 分钟（现状复审成本的 51%）**；治本则是初审前强制校验规则新鲜度。

## 我的判断：看到了什么，根问题是什么

**看到的数据**（剔除 63 行完全重复、48 行 review_ok 缺失后，有效样本 1207 行，退单 143 件，退单率 11.8%，现状人工复审成本 143×90 = 12870 分钟）：

1. **规则滞后是主根因，且差点被漏掉**。`audit_time − rules_synced_at`（两列时区混用 +08:00/Z，已统一为 UTC）全量 ≤ 1 小时、中位仅 0.10h——表面看同步近实时，粗看会误判为非问题。按 5 分钟细分后断崖清晰可见：

   | lag（分钟） | 件数 | 退单率 |
   |:--|--:|--:|
   | =0 | 95 | 2.1% |
   | 0–5 | 496 | 2.6% |
   | 5–10 | 336 | 2.4% |
   | **10–15** | **18** | **61.1%** |
   | 15–60（各段） | — | 30%–50% |

   **lag>10min 的 280 件退单 120 件（42.9%），占 23% 初审量、贡献 84% 退单**；逐日检验 7 天全部成立（每日均数倍高于当日新鲜组），是稳定结构性问题，非单日事故。
2. **token_count 是真信号但主要是 lag 的代理**：>75 段退单率 21.1% 随 token 单调上升；但 token>70 拦下的 28 件退单中 24 件同时在 lag>10min 组，**在规则新鲜的案子里 token>70 退单率仅 4.7%**（低于 16.7% 盈亏线）——独立拦截价值低。
3. **rule_conf_score≤5 是弱信号**：退单率 16.9%，仅略高于盈亏平衡线 16.7%，其余分段平稳在 9–13%。
4. **部门切片暴露一个例外**：华东/华北/西南/跨境 83%–100% 的退单由 lag>10min 贡献（re-sync 可修）；**华南业务中心仅约三成**，且其新鲜组退单率 7.3% 为各部门最高——它的问题不在时滞，需单独排查。

**根问题**：自动初审在规则库同步后 10 分钟以上才执行的案件，大概率带着过期规则审查，被人工终审驳回；「同步近实时」的系统级表象掩盖了这 23% 的半旧窗口。

## 做了什么

1. 数据体检：剔除 63 行完全重复、48 行 review_ok 缺失（不插补、单独报数），统一两列时间戳时区后构造 `lag = audit_time − rules_synced_at`。
2. 假设逐个检验：滞后（5 分钟细分 + 逐日稳定性检验）、token_count（含条件检验排除代理混淆）、conf_score、部门/案件类别。
3. **阈值扫描**（0–55 分钟逐档计算净节省）+ 对照策略网格：净节省 = 90min×命中退单 − 15min×转人工件数，盈亏平衡线 15/90 = 16.7%。
4. 数据质量记录（不作为结论依据）：lag=0 的 95 件退单率仅 2.1%，疑似「同步后立即重跑」的重试队列，仅作观察。

## 怎么证明有用

**阈值扫描**（lag > t 分钟 则转人工）：

| t（分钟） | 转人工 | 命中退单 | 组内退单率 | 净节省 |
|--:|--:|--:|--:|--:|
| >0 | 1112 | 141 | 12.7% | −3990 min |
| >5 | 616 | 128 | 20.8% | +2280 min |
| **>10** | **280** | **120** | **42.9%** | **+6600 min（峰值）** |
| >25 | 212 | 91 | 42.9% | +5010 min |
| >30 | 172 | 73 | 42.4% | +3990 min |

- **最优规则 lag>10min：280 件（23%）命中 120/143（84%）退单，净省 6600 分钟 = 现状复审成本的 51%**；每单期望净赚 90−15=75 分钟。
- **10���25 分钟是 5010–6600 的平台区**：结论对阈值不敏感，过拟合风险可控。
- 对照（同一成本口径）：全部转人工 −5235（初审全废不可取）；token>70 仅 +420，且叠加进 lag 规则反把净节省拉低到 5685（规则新鲜的长卷宗 4.7% 低于盈亏线，转人工亏本）——token 不宜做拦截规则，只适合做人工队列优先级/解析质量监控。
- **治本建议（需 A/B 验证的机制假设）**：初审执行前校验规则新鲜度，lag>10min 先触发 re-sync 再初审（或把同步频率压到 10 分钟内）。若该组退单率回落到新鲜组基线 2.5%，按本数据外推可避免约 113 件退单 ≈ 10175 分钟——比转人工更多，但有同步成本与机制不确定性。

**局限性（如实声明）**：① 转人工后「不再退单」是成本模型假设；② 10 分钟阈值与 61.1% 的断崖段（仅 18 件）为同数据事后选得，单段小样本有噪声——平台区缓解但未消除过拟合风险；③ 数据只有当次记录、规则内容不可见，无法确认因果，lag 也可能是「同步管道停摆」等症状的代理变量——但作为部署规则不妨碍其价值；④ 华南业务中心的新鲜组退单率 7.3% 说明存在时滞之外的退单来源，本数据无法定位。

## 持续优化（追问环节后新增，2026-10-23）

评分版本为追问前的最后一次提交（阈值 0.5h）；追问环节暴露了三个可深挖点，本轮改动（数字全部可由更新后的 `analyze.py` 复算）：

1. **阈值扫描替代手选阈值**：0.5h（净省 3990）改为 **lag>10min（净省 6600，多 66%）**——初版 0.5h 是探索分桶的遗产而非优化结果；扫描显示断崖在 10 分钟、10–25 分钟为平台区。
2. **token 代理检验**：新增条件分析，证明 token>70 的拦截价值大部分来自 lag（28 件命中里 24 件本就在 lag>10min 组；新鲜案子里 token>70 退单率仅 4.7%）。初版把 token 列为「次级信号」偏乐观，现降级为「代理 + 监控信号」。
3. **部门切片**：新增「退单中 lag>10min 占比」表，预演 re-sync 的部门级效果；发现华南业务中心是例外（约三成、新鲜组基线 7.3%），re-sync 对其无效，需单独排查。
4. **治本外推更新**：外推基线从 lag≤0.5h 组 7% 改为新鲜组 2.5%，可避免退单从约 61 件上修为约 113 件（≈10175 分钟）。

## 假设与取舍（不明确处的自行判断）

- 完全重复行按记录剔除（63 行），避免同一案件重复计数；case_id 重复与行级重复一致。
- review_ok 缺失 48 行剔除后单独报数，不插补。
- audit_time（+08:00）与 rules_synced_at（Z）统一转 UTC 后求滞后。
- 「提前转人工」按题给口径理解为在初审环节前移交给人工（15 分钟/件），终审退单按 90 分钟/件计损失。

## 如何复现

Python ≥ 3.12，推荐 [uv](https://docs.astral.sh/uv/)（无 uv 则 `pip install pandas matplotlib tabulate` 等价）：

```bash
uv sync              # 安装锁定版本的依赖
uv run analyze.py    # 唯一入口；CSV 默认读 data/audit_logs.csv
```

- 终端直接打印全部分析；`output/overview.txt`（数据体检）、`output/analysis.txt`（业务分析，README 所有数字出处）、`output/evidence_fail_rate.png`（左：5 分钟分段退单率断崖；右：各部门退单中 lag>10min 占比）。
