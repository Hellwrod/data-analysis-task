# data-analysis-task

> 关灯科技 · 实战任务。只使用任务页发放的 `data/audit_logs.csv`（1318 行），
> 本文引用的每一个数字都来自 `uv run analyze.py` 的输出（`output/analysis.txt`），可逐条复算。

## 一句话结论

**根问题：初审时规则库「半旧」（距最近一次同步 0.5–1 小时）的案件退单率 42.4%，是基线 11.8% 的 3.6 倍**——这 14% 的初审量贡献了 51% 的退单。对这组案件提前转人工初审，按题给成本口径净省 **3990 分钟**（现状复审成本的 31%）；治本则是初审前强制校验规则新鲜度。

## 我的判断：看到了什么，根问题是什么

**看到的数据**（剔除 63 行完全重复、48 行 review_ok 缺失后，有效样本 1207 行，退单 143 件，退单率 11.8%，现状人工复审成本 143×90 = 12870 分钟）：

1. **规则滞后是主根因，且差点被漏掉**。`audit_time − rules_synced_at`（两列时区混用 +08:00/Z，已统一为 UTC）全量 ≤ 1 小时、中位仅 0.10h——表面看同步近实时，容易误判为非问题。但细粒度分桶后出现陡峭阈值：

   | 规则滞后 | 件数 | 退单 | 退单率 |
   |:--|--:|--:|--:|
   | =0h（同分钟） | 95 | 2 | 2.1% |
   | 0–0.5h | 940 | 68 | 7.2% |
   | **0.5–1h** | **172** | **73** | **42.4%** |

   该组逐日退单率 36.0%–53.6%，**7 天全部成立**（见 `output/analysis.txt` §1 逐日表），排除单日事故，是稳定结构性问题。
2. **token_count 是次级信号**：>75 段退单率 21.1%（76 件中 16 退单），随 token 单调上升；在 lag≤0.5h 内部 token>70 也把退单率从 6.0% 抬到 12.8%。超长卷宗的抽取质量劣化真实存在，但强度远弱于滞后维度。
3. **rule_conf_score≤5 是弱信号**：该段退单率 16.9%（225 件中 38 退单），仅略高于转人工盈亏平衡线 16.7%，其余分段平稳在 9–13%。
4. **部门/类别不是抓手**：tenant_dept 最高 15.6% vs 最低 11.3%，dossier_type 最高 15.3%——差异远小于滞后维度（42.4% vs 7.2%），排除结构性差异后不影响主结论。

**根问题**：自动初审在规则库同步后半小时以上才执行的案件，大概率带着过期规则审查，被人工终审驳回；系统级的「同步近实时」表象掩盖了这 14% 的半旧窗口。

## 做了什么

1. 数据体检：剔除 63 行完全重复、48 行 review_ok 缺失（无法评估），统一两列时间戳时区后构造 `lag = audit_time − rules_synced_at`（`analyze.py`）。
2. 假设逐个检验（§1–§3）：滞后（细粒度分桶 + 逐日稳定性验证）、token_count、conf_score、部门/类别，各自的退单率全部分桶算清。
3. 按题给成本口径构建「提前转人工」策略并全网格对比（§4）：净节省 = 90min×命中退单 − 15min×转人工件数，盈亏平衡线 = 15/90 = 16.7%。
4. 数据质量记录（不作为结论依据）：lag=0 的 95 件退单率仅 2.1%，疑似「同步后立即重跑」的重试队列，仅作观察。

## 怎么证明有用

最优简单规则 **lag>0.5h → 转人工初审**：

| 策略 | 转人工件数 | 命中退单 | 组内退单率 | 净节省 |
|:--|--:|--:|--:|--:|
| 现状：不转人工 | 0 | 0 | — | 0 |
| 全部转人工 | 1207 | 143 | 11.8% | **−5235 min** |
| **lag>0.5h** | **172** | **73** | **42.4%** | **+3990 min** |
| token>70 | 140 | 28 | 20.0% | +420 min |
| conf≤5 | 225 | 38 | 16.9% | +45 min |

- 172 件（14% 初审量）命中 73/143（51%）的退单；组内退单率 42.4% 远高于 16.7% 平衡线 → 每转一单期望净赚 90−15=75 分钟。**净省 3990 分钟 ≈ 现状 12870 分钟复审成本的 31%**。
- 信号实时可得：lag 在初审发生时即可由当次记录算得，规则可在线部署。
- 「全部转人工」净节省为负——证明问题不在初审本身，而在对 14% 半旧窗口的精准补位。
- **治本建议（需 A/B 验证的机制假设）**：初审执行前校验规则新鲜度，lag>0.5h 先触发 re-sync 再初审（或把同步频率加密到 30 分钟内）。若该组退单率回落到 lag≤0.5h 组的 ~7%，按本数据外推可避免约 61 件退单 ≈ 5490 分钟，比转人工更省。

**局限性（如实声明）**：① 转人工后「不再退单」是成本模型假设，实际法务把关也可能仍有疏漏；② 0.5h 阈值为同数据事后选得，有过拟合风险，解读口径为「若该模式成立」；③ 无法确认因果（数据只有当次记录，规则内容不可见），lag 也可能是「同步管道停摆」等症状的代理变量——但作为部署规则这不妨碍其价值。

## 假设与取舍（不明确处的自行判断）

- 完全重复行按记录剔除（63 行），避免同一案件重复计数；case_id 重复与行级重复一致。
- review_ok 缺失 48 行剔除后单独报数，不插补。
- audit_time（+08:00）与 rules_synced_at（Z）统一转 UTC 后求滞后。
- 「提前转人工」按题给口径理解为在初审环节前移交给人工（15 分钟/件），终审退单按 90 分钟/件计损失。

## 如何复现

Python ≥ 3.12，推荐 [uv](https://docs.astral.sh/uv/)（无 uv 则 `pip install pandas matplotlib tabulate` 等价）：

```bash
uv sync              # 安装锁定版本的依赖
uv run analyze.py    # 唯一入口；CSV 默认读 data/audit_logs.csv
```

- 终端直接打印全部分析；`output/overview.txt`（数据体检）、`output/analysis.txt`（业务分析，README 所有数字出处）、`output/evidence_fail_rate.png`（滞后×token 退单率图）。
